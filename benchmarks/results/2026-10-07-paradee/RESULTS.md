# Native Paradee CPU sanity validation

2026-10-07, this workstation, OpenVINO 2026.4 CPU, eSpeak NG 1.52.0 native
frontend, two OpenVINO CPU threads, debug Rust build. Official FP32 model and
metadata use the hashes pinned in `src/catalog.rs`. No ORT process or library is
used by this integration. An isolated eSpeak build under `/tmp` was used; no
system package, configuration, model installation or default was changed.

The [measurements](native-cpu.json) record one cold load and warm generation of
short text, abbreviations/numbers, and a long passage. Every returned sample was
finite; peaks were nonzero and below clipping. The long passage yielded three
PCM chunks, first before generation completed. WAV outputs were written to
`/tmp/paradee-survey/native-utterance-{0,1,2}.wav` during the probe and are not
committed.

This establishes native frontend → OpenVINO → PCM execution and segment delivery.
It does not establish perceptual quality or parity with the author's full Misaki
lexicon. The profile remains experimental; a fixed pronunciation/listening corpus
is required for broader qualification. Internal punctuation handling and unusual
names are known frontend limits documented in `docs/PARADEE.md`.

Nine focused unit tests cover upstream spelling-map examples, padding and
nontruncating long-phoneme segmentation, rejection of unknown/empty phonemes,
CPU-only catalog placement, voice inventory, pinned footprint and asset path
validation, concurrent pipe-filling frontend I/O, output bounds, blocked-input
timeouts and synthesis-parent death. All nine focused tests pass. The original
202 library tests passed before this additional subprocess hardening, with
socket/download fixtures enabled. CPU execution was subsequently checked using
`EXECUTION_DEVICES`, with 136,200 finite samples generated by the updated backend.
Clippy passed with the existing unrelated `collapsible_if` warnings in the D-Bus
module allowed. See `docs/AUDIOCPP-PARADEE-FOLLOWUP.md` for future provider work.
